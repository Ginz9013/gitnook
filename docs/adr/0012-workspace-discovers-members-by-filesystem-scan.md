# Workspace 用檔案系統掃描探測成員，不讀 .gitmodules 或設定檔

Workspace 的成員 Board 由遞迴掃描檔案系統找出：只問某個子目錄底下有沒有
`.issues/issues/`，找到就不再往它底下更深處找，並跳過 `.git`、`node_modules`
（兩者已知不可能含使用者自建的 `.issues/`，跳過純粹省時間，不影響正確性）。

我們刻意不讀 `.gitmodules`——那會把 Workspace 限定在只認 git submodule，排掉
「母資料夾底下並排幾個一般子資料夾／獨立 repo」這種同樣常見的形狀。我們也刻意
不要求一個列出成員的設定檔——同 ADR-0002「沒有 sqlite、沒有衍生快取」的精神：
`.issues/` 本身已經是唯一的真相來源，Workspace 不該在旁邊再放一份需要手動維護、
可能與實際目錄結構脫節的成員清單。

代價是掃描必須走過整棵目錄樹而非讀一份現成清單，但「找到 Board 就停止往下鑽」
加上跳過兩個已知不含 `.issues/` 的目錄，讓這個代價在實務上可接受。

## Considered Options

- **讀 `.gitmodules`**：只在乎 git submodule，排除一般子資料夾並排的用法，且
  submodule 尚未 checkout 時目錄是空的，仍然需要退回檔案系統判斷。
- **設定檔列出成員路徑**：使用者要手動同步一份清單，目錄結構一變就可能過期，
  而且沒有任何東西會提醒清單已經過期——這正是 nook 一貫拒絕的「靜默漏資料」。

## Consequences

因為沒有設定檔，Workspace 沒辦法排除某個「明明有 `.issues/` 但使用者不想被算
進來」的子目錄。如果之後真的出現這種需求，那才是加一份排除清單的理由，而不是
現在預先加一個大概率不會被用到的旗標。
